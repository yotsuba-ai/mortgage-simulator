# deep-iterate — 緑になるまで回す

## これが解く問題

コード編集で最も高くつく失敗は、バグではなく **「たぶん直った」で手を止めること** です。
確認していない変更は、後で人間がデバッグし直す宿題になり、直す前より状況が悪くなることさえあります。

このスキルは、その宿題を出さないための手順です。中心にあるのは 1 つの考え方 —
**「動いたはず」を「実行して確かめた」に変換する経路を、作業の最初に用意する。**
その経路さえあれば、反復は安く速くなり、何十回でも回せます。無ければ 1 回目から博打になります。

回数そのものは目的ではありません。回数は「判定が自動化できている」ことの結果です。

## 全体の流れ

```
0. 完了条件を実行可能な形にする   ← ここを飛ばすと永久に終わらない
1. 観測して仮説を立てる           ← 手を動かす前に読む
2. 判定ハーネスを用意する         ← 1 コマンドで赤/緑が出る状態
3. 赤 → 緑 のループを回す         ← 1 回に 1 仮説
4. 自分の差分を攻撃する           ← 緑になった後が本番
5. 緑の地点でコミットする         ← 戻れる場所を作る
```

## Phase 0 — 完了条件を実行可能な形にする

作業開始時に「何が起きたら完了か」を、**実行して真偽が判定できる文** に落とします。

- 悪い: 「シミュレーターの計算を正しくする」
- 良い: 「元利均等の月返済額が 3000万円 / 年1.0% / 35年 で 84,686円 ±1円」
        「金利0%でも NaN を返さない」「返済期間終了時の残債が 0 になる」

曖昧な要求は、ここで数個の判定可能な文に翻訳してからユーザーに見せると、
認識のズレが実装後ではなく実装前に見つかります。仕様が本当に決まらない部分は
仮定を1行明記して進め、判定文にも仮定として残します。

## Phase 1 — 観測して仮説を立てる

編集を始める前に、実際のコードと実際の失敗出力を読みます。推測で書いた修正は、
たとえ通っても「なぜ通ったか」が分からず、次の変更で崩れます。

- 関連コードを読む（呼び出し元・呼び出し先まで）
- 失敗しているなら、その出力を **全文** 読む。要約や思い込みで代用しない
- 「原因は X だと思う。なぜなら出力の Y がそう示している」まで言語化する
- 分からないなら、修正ではなく **観測を増やす**（中間値の出力、最小再現の作成）

ここで時間を使うほど Phase 3 が短くなります。逆にここを飛ばすと、Phase 3 が
「当てずっぽうを高速に繰り返す装置」になり、時間もトークンも溶けます。

## Phase 2 — 判定ハーネスを用意する

**1 コマンドで赤か緑かが出る状態** を作ります。目安は数秒〜十数秒。
遅いハーネスは回数を減らし、回数が減ると反復の価値が消えます。

プロジェクト種別ごとの作り方、テストが 1 つも無い場合の始め方、
単一 HTML ファイルのアプリを Node で検証可能にする手順は
`references/harness.md` を読んでください。同梱の
`scripts/extract-inline-js.mjs` は、HTML 内のインライン JS を抜き出して
Node から関数を直接呼べるようにする道具です（テスト基盤ゼロの状態から
数十秒で最初の 1 本が書けます）。

既存のテストがあるなら、まず **今の状態で実行して緑を確認** します。
最初から赤いなら、それは自分の変更のせいではないと後で分かる貴重な基準線です。

## Phase 3 — 赤 → 緑 のループ

```
変更する（1回に1つの仮説だけ）
  → ハーネスを実行する
    → 出力を全文読む
      → 緑なら次の判定文へ / 赤なら「なぜ」を更新して繰り返す
```

このループを健全に保つ約束事:

- **1 回に 1 仮説。** 3 箇所同時に変えて緑になっても、何が効いたか分からない。
  赤に戻ったときに切り分けられなくなり、結局やり直しになります。
- **同じ失敗が 2 回出たら、修正ではなく観測を足す。** 同じ場所を別の書き方で
  叩き続けるのは、仮説が間違っているサインです。ログを増やす、入力を最小化する、
  1 段下のレイヤーを直接呼ぶ。
- **3 ラウンド収束しなければ、問題の切り方を変える。** 再現を最小化する、
  一度変更を捨てて別経路で書き直す、のどちらか。同じ方向に 4 回目は投じない。
- **テストを緩めて緑にしない。** skip、期待値を実測値に書き換える、アサーションを
  消す — これらは緑ではなく、赤を隠した状態です。期待値を変えてよいのは
  「仕様の理解が誤っていた」と根拠つきで説明できるときだけで、そのときは
  ユーザーにその 1 行を伝えます。
- **緑を報告する前に、必ず最後にもう一度全体を実行する。** 途中の緑は、後の変更で
  失われていることがあります。

失敗モードの見分け方と抜け方の一覧は `references/loop-discipline.md` にあります。

## Phase 4 — 自分の差分を攻撃する

緑は出発点で、終点ではありません。ハーネスが通ったら、自分の diff を
「これを壊すとしたらどの入力か」という目で読み直します。特に効くのは:

- **境界値**: 0、1、負値、空、極大値、期間 0、金利 0%
- **数値の質**: 丸め、桁あふれ、浮動小数の比較、NaN / Infinity の伝播
- **単位**: 万円と円、年率と月率、%と小数 — 単位混同は型では捕まりません
- **回帰**: 触っていない機能が、共有している関数経由で壊れていないか
- **状態**: 実行順序、キャッシュ、保存済みの古いデータ

見つかった穴は「気をつける」ではなく **判定文を 1 つ足して** 埋めます。
そうすれば次の変更でも自動で守られます。

## Phase 5 — 緑の地点でコミットする

緑になったら、その時点でコミットします。理由は履歴の綺麗さではなく、
**次の実験を安心して壊せるようにするため** です。戻れる地点があると、
大胆な変更を試すコストが下がります。

コミットメッセージには「何を」だけでなく「なぜ」と「どう確認したか」を短く残します。

## 止まってユーザーに聞くべきとき

自律ループの価値は、聞かなくていいことを聞かないことにありますが、
以下は判断を持ち帰るべきです:

- 仕様そのものが分岐する（どちらの挙動も妥当で、選択が業務判断）
- 失敗の原因が、依頼範囲の外にある設計上の問題
- 破壊的な操作（データ削除、履歴の書き換え、外部への公開）が必要
- 3 ラウンド以上収束せず、観測を増やしても仮説が立たない

聞くときは、選択肢と自分の推奨、そして「なぜ判断が必要か」を添えます。
止まらずに聞ける部分（依存しない残りの作業）は先に進めておきます。

## 報告のしかた

最後の報告では、次を事実として書きます — 誇張も過度な留保もなしに:

- 何を変えたか
- どの判定文が今どうなっているか（緑 / 赤 / 未検証）
- 検証していない部分があるなら、それがどこで、なぜか

「たぶん動きます」は報告ではありません。実行結果か、未検証である旨のどちらかを書きます。
