# Deep Loop — 自律的に回して仕上げる

## このスキルが解こうとしている問題

長い実装タスクで失敗するときの原因は、たいてい「頭の良さ」ではなく **前進しているかどうかを判定できないまま手を動かし続けること** です。判定手段がない状態でループを回すと、もっともらしい編集が積み上がるだけで品質は上がらず、時間とトークンだけが消えます。

逆に、機械的に真偽を返す検証シグナルが 1 つでもあれば、ループは自動的に前へ進みます。だからこのスキルの中心は「速く書く」ことではなく、**検証を先に用意し、毎回それに突き当てること**です。

## 0. 検証シグナルを先に確保する（省略しない）

コードを書き始める前に、「今の変更が正しいかを機械が答えてくれる仕組み」を特定します。

1. **既にあるか探す** — `package.json` の scripts、`Makefile`、`pytest`、CI 設定、`.claude/skills/` の他スキル、README の実行手順。あるなら**まず一度そのまま実行し、変更前の状態（グリーンか、既に赤いか）を記録**します。この基準点がないと、自分が壊したのか元から壊れていたのか永遠に区別できません。
2. **なければ作る** — ここを飛ばしたくなるのが最大の罠です。小さくていいので、対象の中心的な振る舞いを 1 コマンドで判定できるものを最初に作ります。作り方の具体例は `references/verification-recipes.md` を読んでください（テストが無いプロジェクト、単一 HTML ファイル、CLI、API、UI など類型別に置いてあります）。
3. **どうしても機械判定にできない場合**（見た目の良し悪し、文章のトーンなど）は、判定者が人間であることを自覚し、**ループを短く切って早めに見せる**。主観的な対象を自分だけで何十回も回すのは、ほぼ確実に無駄になります。

検証シグナルは「速いこと」が価値です。1 回 10 分かかる全体テストしかないなら、対象部分だけを叩く数秒のコマンドを別途用意し、それを内側のループに、重いものを終盤の確認に使います。

## 1. 計画と台帳（ledger）を書く

作業ディレクトリの外（スクラッチ領域）に進捗台帳を 1 ファイル作ります。理由は 2 つあり、どちらも実務的です。**会話が長くなると前半の文脈は圧縮されて消える**こと、そして**自分が今どの仮説を検証中なのか見失うと同じ失敗を繰り返す**ことです。

```markdown
# <タスク名>
## ゴール（何ができたら完了か、検証コマンドで書く）
- [ ] `<検証コマンド>` がグリーン
## 変更前の基準点
- <実行結果の要約。元から失敗しているものがあればここに列挙>
## 作業単位
- [x] 1. <小さな単位> — 検証: <結果>
- [ ] 2. <小さな単位>
## 学んだこと / 却下した仮説
- <仮説とその反証。同じ穴を二度掘らないための欄>
```

作業単位は「1 単位 = 1 回の検証で正否が分かる大きさ」に割ります。大きすぎると失敗したとき原因が特定できず、切り分けのためのやり直しで結局遅くなります。

## 2. ループを回す

1 周はこの 5 手です。**1 周で変える対象は 1 つ**に保ってください。同時に 3 箇所いじると、赤が出たときにどれが原因か分からず、ループが情報を生まなくなります。

1. **仮説を立てる** — 「X が原因だ」「Y を足せば通る」を言語化する。言語化できないなら、まだ調査が足りません。
2. **最小の変更を書く** — 仮説を試すのに必要な分だけ。ついでの整理は別の周でやります。
3. **検証を実行する** — 推測で終わらせない。実行して出力を得る。
4. **出力を実際に読む** — 「たぶん通った」ではなく、終了コードと本文を読む。ここを飛ばすと、通っていないものを完了と報告する事故が起きます。
5. **台帳を更新する** — 通ったらチェック、落ちたら「学んだこと」に反証を書く。

### 赤が出たときの診断

再実行は診断ではありません。同じコマンドを黙って 2 回叩いても新しい情報は増えません。落ちたら次の順で**情報を増やす**こと。

- エラーメッセージと、それが指す行を実際に開いて読む
- 期待値と実際値を並べて、**どこから乖離したか**を特定する（結果ではなく分岐点を探す）
- 分からなければ**安いプローブを足す**（途中値のログ出力、アサーション、入力を極端に単純化した最小再現）。プローブは仮説を確定させてから消す
- 直したら、**同じ検証を必ずもう一度**実行する

3 周連続で新しい情報が出ていない（同じ場所で同じように落ちている）なら、それはループの外に原因があるサインです。手を動かすのをやめて、前提そのもの（環境、依存、そもそも仕様の理解）を疑ってください。

### やってはいけないこと

これらは「グリーンに見せる」だけで、実際の問題は残ります。後で必ず高くつくので選ばないでください。

- テストを削る / スキップする / 期待値をバグに合わせて書き換える
- 型チェックや lint を無効化する、`any` や `# type: ignore` で黙らせる
- 例外を握りつぶして通ったことにする
- 原因が分からないまま「たぶんフレーク」で片付ける（本当に環境要因なら、その根拠を示せるはずです）

検証が要求していることが不合理だと判断したなら、黙って回避するのではなく、**そう考える理由と代案を報告**してください。判断はユーザーのものです。

## 3. いつ止めるか

自律ループの価値は「止め時を自分で判断できること」まで含みます。次のいずれかで止めて報告します。

- **完了**: ゴールの検証がグリーンで、既存の検証も壊していない（変更前の基準点と比較して確認する）
- **行き詰まり**: 同じ根本原因で 3 周以上進展がない。何を試して何が分かったかを添えて報告する
- **範囲外**: 直すのに、頼まれた範囲を超える設計変更や仕様判断が要ると分かった。提案を添えて確認する
- **不可逆**: 破壊的操作（データ削除、外部への送信、履歴の書き換え）が必要になった。実行前に確認する

止まるときに一番大事なのは正直さです。**通っていないものを通ったと言わない。**「3 件中 2 件はグリーン、残り 1 件は〇〇が原因で未解決」と書くほうが、曖昧な完了報告よりずっと役に立ちます。

## 4. ループを安く回す

長時間の自律ループは、無駄な手数がそのまま消費になります。品質を落とさずに効率を上げる手は決まっています。

- **依存のない操作は 1 ターンにまとめて並列で投げる**（複数ファイルの読み込み、独立した検索、独立したチェック）
- **狭い検証を内側、重い検証を外側に置く**。全体テストは節目でだけ回す
- **ファイル全体の再読み込みを避ける**。必要な範囲を指定して読み、grep で位置を特定してから開く
- **長い出力は要約して台帳に落とす**。同じログを何度も文脈に載せない
- **時間のかかるビルドやテストはバックグラウンドで走らせ**、その間に読める場所を読む
- **同じ手順を 3 回書いたらスクリプトにする**。以降の周が短くなり、手順のブレも消える

「たくさん回す」こと自体は目的ではありません。**1 周あたりの情報量を増やす**ことが目的です。

## 5. 最後にやること

- 変更点を通しで読み返す（自分の diff を、レビュアーの目で一度読む）
- ゴールの検証と、変更前にグリーンだった検証の両方を最終実行する
- 報告に書く: **何を変えたか / 何を実行して確認したか（コマンドと結果）/ 確認できていないもの / 残した判断**
- 台帳の「学んだこと」で、コードに残すべき知見があればコメントや README に移す
